## Key decisions to carry forward

- **Custom domain DNS lives in Squarespace's UI, but the actual nameservers are Google Cloud DNS.** aribajahan.com was originally a Google Domains registration; Squarespace acquired Google Domains in 2023 and migrated those domains into Squarespace Domains management, but the underlying DNS backend stayed on Google Cloud DNS. Practically this didn't matter — Squarespace's own DNS records UI still edits it directly, no separate Google Cloud console access was needed. Vercel's dashboard labeling records as "at Google Cloud DNS" was just naming the actual backend, not asking for a different login. Squarespace's DNS panel had Squarespace's own default hosting records (4 A records on `@` pointing to Squarespace IPs, plus a `www` CNAME to `ext-cust.squarespace.com`) that had to be removed/replaced with Vercel's A record (`216.198.79.1`) and CNAME (`a50a7005bf9436d6.vercel-dns-017.com.`) — but the MX records (Google Workspace email) and the two verification CNAMEs (Google site verification, Squarespace verification) were left untouched since removing those would have broken Ariba's email.
- **Contact form delivery: Resend over Formspree**, chosen so submission content stays in Ariba's own infrastructure (a Vercel API route she controls) rather than passing through a third party, and because Resend's free tier (3,000 emails/month) comfortably outlasts Formspree's (50/month). The API route lives at `app/api/contact/route.ts`; `RESEND_API_KEY` must be set in **both** `.env.local` (local dev) and Vercel's project env vars (production) — they don't share state, so adding it in one place only breaks the other environment silently.
- **`Nav`'s `contactHref` prop now defaults to `/contact`** (was `#close`, a dead anchor). Also fixed a pre-existing bug where the *mobile* nav's Contact link was hardcoded to `#close` and ignored the prop entirely — it now respects `contactHref` like the desktop version does. Per-page closing-CTA sections (their own `mailto:` or `#close` scroll targets) were deliberately left untouched — this only changed the top-nav Contact button's destination site-wide.

- **Mock pixel values need empirical recalibration, not blind trust.** This was the single most expensive lesson of the session, learned twice: (1) the Substack embed's crop offset, and (2) the Speaking logo grid's column-width and per-logo heights. In both cases, copying the design mock's literal CSS values produced a visibly wrong result once actually rendered in this site's real container widths/fonts. The fix both times was to measure the *live rendered* result (via `getBoundingClientRect`, or literal on-screen marker lines drawn with `javascript_tool` for pixel-precise calibration) and iterate from there — not to assume the mock's numbers transfer 1:1. When implementing a Claude Design mock, treat its pixel values as a starting hypothesis, always verify live before calling it done.
- **Substack embed technique** (`SubstackEmbed.tsx`, used on Home): Substack's `/embed` iframe is cross-origin, so its internal title/description/colors can't be restyled by us — only cropped out of view. The iframe is always rendered at its natural 480px width (so text reflow stays consistent with the calibration) and the whole cropped block is scaled down via CSS `transform: scale()` for different display sizes, rather than giving the iframe itself a narrower width (a narrower iframe reflows its internal text differently and throws off the crop). Current calibration: email/button row starts at y=330, 110px tall window through the fine print + logo. The internal button color is controlled by Substack's own publication-level "Accent color" setting (Settings → Branding → Edit theme) — Ariba set hers to `#E73131`, but Substack applies its own lightened/softened tint of that accent for this specific button, not the raw hex; that's the ceiling of what's controllable.
- **Speaking's logo/gallery section was consolidated** from two separate components (`TrustedByLogos` + `EngagementsGallery`) into one (`SpeakingEngagements`), matching a new Claude Design mock. Key specifics: no "Show More" at desktop (full 36-logo grid always shown); mobile/tablet show the 12 most broadly-recognizable logos (3 rows) with a Show More toggle — the *order* of `speakingLogos` in the data file determines which 12 that is, so reordering that array changes what's visible by default. Logo grid uses `minmax(110px,1fr)` (not the mock's stated 120px — see recalibration note above). The photo gallery's second row is its own separate 3-column grid (not row-spanning into the first row's grid) specifically to avoid a phantom empty cell that a 4-column/2-row grid produces when the hero photo spans 2×2 and only 4 more single photos exist to fill the remainder.
- **Logo asset quality varies — check individual files, don't assume uniform padding.** The UN logo had zero padding above the emblem and 39px below, which made `items-center` grid alignment visibly misalign it against its row-mates; fixed by re-cropping the source PNG with `python3`/PIL to symmetric padding. Some logos (Columbia University, UN) also needed larger `heightPx` than others at the same nominal size, because detailed crest/seal-style marks read as "tinier" than bold wordmarks at equal file height — this is a per-logo judgment call, not a formula.
- **Voice: first-person, not third-person.** "Bring Me to Your Event" (not "Bring Ariba..."), "More About Me" (not "...Ariba"). Applied across Speaking hero/closing-CTA/trusted-by and Home's Recognition section — check for `Ariba` in third-person CTA copy before adding new ones.
- **`Nav` takes an optional `contactHref` prop**, now defaulting to `/contact` (see the Resend-session entry above for the full history — it used to default to the dead `#close` anchor).
- **Section-opening padding standard: 70px mobile / 96px tablet (max-[1024px]) / 120px desktop**, applied consistently across all four pages. Exceptions that deliberately stay off this rhythm: `Positioning`/`AboutIntro` (56px intro paragraphs), `WwmTrustedBy`/`TwoWaysDivider` (compact interstitial bands), `CareerAdvisory` (centered layout), and stat-strip/compact bands like `Credentials` (uses `py-14`/`py-10`, not the full rhythm — it's a thin numbers band, not a full editorial section, and the full rhythm made it look oversized relative to its content).
- **Testimonial truncation is mobile *and* tablet**, clamped with a Read more/Show less toggle; desktop always shows full quotes. The toggle button's visibility is decided by a static character-count heuristic, which is only accurate at the narrowest width it was tuned for — a quote that needs clamping on a 375px card may not need it on a wider tablet card, producing a "Read more" button that reveals nothing new. Known limitation, not yet fixed everywhere; when auditing testimonials, check actual rendered overflow (`scrollHeight > clientHeight`) at each breakpoint, not just whether the button appears.
- **Never overwrite an image file in place** for user-provided photos — always save under a brand-new filename. (Re-cropping an *existing sourced asset* like the UN logo for a genuine bug fix is a different case — that was a deliberate in-place correction, tracked via git.)
- **Tailwind v4 cascade gotcha:** plain CSS targeting a bare HTML tag in `globals.css` must be wrapped in `@layer base { ... }` or it beats every layered utility class regardless of specificity.
- **Dropped source images live in `design-reference/assets/`, not `public/assets/`** — copy into `public/assets/` under a distinct filename before they'll render. `public/uploads/` is the other asset location in active use (gallery/speaking photos).
- **Git author** is set at the repo level to `4304091+aribajahan@users.noreply.github.com` — don't let this drift back to a hostname-based auto-detected email.
- **Reading Room stays untouched** until Ariba explicitly says to start it — its nav link is removed, not just the page unbuilt.
- **Be proactive about spacing/rhythm consistency, not reactive** — check padding/margin/sizing consistency as part of finishing a section, across every page and breakpoint it touches, not after Ariba points it out.

## Process notes for next session

- **Vercel**: no MCP connector exists in this environment's registry. Deployment goes through Ariba's own Vercel dashboard — Claude can't do this on her behalf, only guide her through it and verify the result afterward.
- **`python3` + PIL are available** and useful beyond obvious image editing: computing a PNG's actual ink bounding box (`img.getbbox()`) to check for asymmetric transparent padding, checking real pixel dimensions before setting display sizes, cropping/re-padding assets. Used successfully this session to fix the UN logo and to crop the OG share image.
- **`getBoundingClientRect()` must be called in a fresh tool call after a scroll, not the same one that triggered the scroll** — `window.scrollTo()` followed immediately by reading a rect in the *same* `javascript_tool` call can return stale/pre-scroll coordinates. Split into two calls when precise positioning matters.
- **`getComputedStyle(el).display` does not reflect an ancestor's `display:none`.** A child inside a hidden parent still reports its own specified display value. To check whether an element is *actually* visible, use `getBoundingClientRect().width > 0` (or similar), not `getComputedStyle`.
- **The in-app Browser pane tool is still flaky** — screenshots/navigation periodically return stale state (e.g. a stale console error persisting across navigations, or a page appearing not to update after a file edit). Fix that reliably works: `tabs_close` the stuck tab, then `preview_start` again for a fresh one. Don't keep retrying the same call.
- For scrolling to a specific section reliably, prefer `element.offsetTop` (stable, absolute) over `getBoundingClientRect().top` combined with a running `scrollTo` (relative to current scroll position, easy to double-apply or miss).
- For auditing padding/margin/sizing site-wide, a small JS snippet via `javascript_tool` (walk elements, read `getComputedStyle()` or `getBoundingClientRect()`) at each target viewport width (375 mobile / ~900 tablet / 1400 desktop) is far more reliable than eyeballing screenshots.
- When a user pastes/uploads an image directly into chat (not via a file path), there is no accessible file on disk — ask them to save it somewhere reachable (Desktop, Downloads, or directly into `design-reference/assets/`) before it can be used.
